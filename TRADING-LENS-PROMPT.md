# Trading Lens — complete project context

Paste this as context when you want an AI (or a new collaborator) to understand
the whole application before touching it. It describes what exists as of
**7 September 2026**, not what is planned.

---

## What it is

**Trading Lens** is a personal trading journal. A trader logs every position
they take — entry, exit, size, stop, target, the strategy they used, how they
felt, and whatever custom fields they invent — and the app turns that log into
performance analytics, statistical insights, and (on the paid plan) AI analysis
of their own execution.

It is single-tenant per user: everyone sees only their own data, enforced by
Postgres row-level security rather than by application code. There is no
social feed, no copy-trading, no broker integration. It is a private notebook
that does arithmetic.

**The product principle**, which explains most of the design decisions below:
*a fabricated number is worse than no number.* A trader may act on what this
app tells them, so every figure has to trace back to a row they entered.

## Architecture and conventions

Follow these rather than introducing new patterns — every one of them was
arrived at by fixing something.

**Auth.** `src/proxy.ts` is the *only* place that verifies the session with
Supabase Auth. It forwards the resolved id downstream in an `x-user-id` header
(stripped from the incoming request first, so a client cannot forge it). API
routes read it with `getUserIdFromHeader()` and return 401 on null; server
components use `requireUserId()`. Nothing else calls `getUser()` — that was a
second network round-trip on every request.

**Data access.** Three clients, and which one you use is a security decision:
- `src/lib/supabase/server.ts` — RLS-scoped, the default for everything
- `src/lib/supabase/client.ts` — browser, anon key (public by design)
- `src/lib/supabase/admin.ts` — service-role, **`server-only`**, bypasses RLS.
  Used only by the analytics RPCs, account deletion, and the admin plan route

**Business logic** lives in `src/lib/<domain>/` (38 directories) as
`queries.ts`, `schema.ts`, `types.ts`. Routes are thin: parse, validate,
delegate, respond.

**Validation.** Every mutating route validates its body with a zod schema and
returns the first issue's message. Bounded strings with explicit messages, so a
bad payload is a clean 400 rather than a 500 from Postgres.

**Paging.** `fetchAllRows()` — PostgREST silently caps an un-limited select at
1,000 rows and returns *success*. Any query that aggregates "all rows" must use
it or it will quietly go wrong for exactly the users with the most data.

**One definition per statistic.** `src/lib/segments/engine.ts` is the single
implementation of win rate, expectancy, profit factor, average win/loss and max
drawdown over any slice of the journal. It exists because four features had
grown four subtly different copies. `summariseSegment` is **order-dependent**
(max drawdown is a walk, not a sum), so callers pass trades chronologically.
`MIN_SEGMENT_TRADES` / `MIN_SEGMENT_WITH_R` are the sample floors below which a
comparison is withheld entirely rather than shown with a caveat nobody reads.

**Expectancy is in R, not dollars.** `rSum / rCount` over the trades that
carry an R multiple. Rendering it with a `$` has been a real bug twice; it is
also computed over a *subset* of trades, so any UI showing it must be able to
say how many.

**Timezones.** `src/lib/dates/local-day.ts`. Everything user-facing buckets by
the trader's own calendar day, never UTC's. This app has shipped and fixed this
bug twice: for anyone west of UTC an evening trade lands in tomorrow's UTC day.

**Comments explain *why*, not *what*.** The codebase reads as a record of
decisions — what was tried, what broke, what the alternative would have cost.
Match that density; it is the house style.

**Tests** cover pure logic: computation, parsing, validation, date maths,
security properties. **64 files, 920 tests.** No component or E2E tests.

## Migrations — read this before touching the database

`supabase/migrations/0000` … `0039`. **There is no migration runner.** Every
file from 0020 onward carries a `MANUAL APPLY REQUIRED` header meaning someone
pastes it into the Supabase SQL editor by hand. Nothing in the repo records
which are live.

Consequences you must design around:
- A migration in git is **not** a migration in the database
- Code must degrade gracefully when a table or column is missing — detect it
  (`42P01` / `PGRST205` for tables, `PGRST204` / `42703` for columns, via
  `src/lib/supabase/errors.ts`) and return an actionable "a migration is
  pending" message rather than a bare 500
- The live database is applied through **0039**. 0000-0038 were verified on
  4 Sep 2026 by a real `select` against each table; 0039 (`order_types`) was
  applied by the operator on 7 Sep 2026 and is reported as run, not
  independently verified here
- **Never probe with `head: true`** — a head query returns no error and a null
  count on a *missing* table, so it reports success either way. That false
  positive has been believed once

## Data model

**19 tables.** `trades` is the centre; almost everything else hangs off it.

| Table | Purpose |
|---|---|
| `trades` | Every position. Core columns plus a `custom_fields` jsonb blob |
| `field_definitions` | User-defined fields — the schema is data, not code |
| `user_settings` | One row per user: hidden fields, dashboard layout, timezone, `is_admin`, `has_completed_tour`, `plan` |
| `folders` / `trade_folders` | User-made groupings, many-to-many |
| `strategies` / `trade_strategies` | Named setups with descriptions, many-to-many |
| `trade_history` | Automatic pre-edit snapshots (trigger), with retention |
| `trade_images` | Chart screenshots in Supabase Storage |
| `account_transactions` | Cash ledger — deposits and withdrawals |
| `commission_rules` | Per-user broker fee rules |
| `analytics_events` / `analytics_sessions` | Self-hosted product analytics |
| `user_api_keys` | Encrypted BYO AI provider keys |
| `ai_provider_consents` | Per-provider data-sharing agreement |
| `ai_reviews` | Generated AI reviews, trade and period |
| `strategy_rules` | Checkable plan rules attached to a strategy |
| `trade_excursions` | Measured MAE / MFE per trade, with a status enum |
| `goals` | Process and outcome goals, with a shape CHECK per kind |

`trades` also carries `dismissed_suggestions text[]` (0037) — tag suggestions
the trader turned down. It is a column rather than a `custom_fields` key
because custom_fields is the trader's *own* data: it is exported and fed to
every AI prompt under their own labels, and an internal flag has no business
appearing there as though they had written it. 0039 adds `order_type` and
`time_in_force` as `text + CHECK` rather than enums, deliberately — extending a
Postgres enum needs `ALTER TYPE ... ADD VALUE`, which cannot run in the same
transaction that adds it.

**9 RPCs**: `dashboard_stats` (one round trip for the dashboard), four
`admin_*` aggregates, and the trigger functions `set_updated_at`,
`snapshot_trade_history`, `seed_default_field_definitions`, `seed_user_settings`.

**The history trigger interacts with its own retention cap.**
`snapshot_trade_history` fires `before update … for each row`, and 0023 keeps
only the newest 50 snapshots per trade. So *any* write to `trades` spends one
of those fifty slots and can evict a real edit. 0038 makes the trigger skip
updates that changed nothing but `dismissed_suggestions` (or nothing at all);
anything else that adds a housekeeping column to `trades` must extend that
exclusion or it will quietly delete the user's edit history.

**RLS everywhere**: `for all using (auth.uid() = user_id)`.

### Two schema rules that are load-bearing

**1. `trades.dollar_pl` is stored NET of commission.** Every aggregate in the
app — dashboard, analytics, insights, ask, AI reviews, the RPCs — sums or
thresholds this one column, so none of them need to know commissions exist.
`dollar_pl > 0` is how *every* win rate in the app is defined, and it means
"actually made money", not "made money before the broker's cut".

**2. Column grants are a security control.** Migration 0024 fixed a privilege
escalation: RLS constrains which *rows* a user may write and cannot express
which *columns*, so a user could set their own `is_admin = true` from devtools
with the public anon key. The fix revoked table-level write on `user_settings`
and re-granted a specific column list. **A newly added column therefore starts
with no write privilege — that default is the control.** `is_admin` and `plan`
are both absent from those grants and must stay absent. Never restore a
table-wide `grant update on user_settings`.

## Feature inventory

**26 pages, 49 API route handlers** (plus `/auth/confirm`).

### Trades — the core
- **`/trades`** — searchable, sortable, filterable list. Search is treated as
  data, never as filter syntax
- **`/trades/[id]`** — the trade card. Autosaves as you type, with debounce and
  flush-on-blur. Derived fields (P&L, %, R multiple, R:R) are computed
  server-side and never accepted from the client
- **Two modes**: `trade` (has realised P&L) and `investment` (a long-term hold;
  carries no entry/exit P&L, so it is **excluded from every performance
  statistic** — counting it would inflate denominators with positions that can
  never win)
- **Three statuses**: `pending` → `open` → `closed`
- **Version history** — every edit snapshotted by trigger, viewable and
  restorable. Restore re-derives P&L rather than trusting the snapshot, so an
  old pre-commission snapshot can't write back a gross number
- **Chart screenshots** — uploaded to Storage, served by batched signed URL
- **OCR** — drop a broker screenshot and it fills the form. Multi-pass pipeline
  (preprocess → OCR variants → classify → layout → semantic parse → dedupe →
  cross-validate), with per-field confidence badges
- **Price chart** per trade, from Yahoo's public chart endpoint
- **Auto-execution** — a cron sweep fills pending orders whose price was hit,
  guarding against stale quotes (a session's high/low doesn't reset until the
  next open, so an evening order could otherwise fill against a range that
  finished hours earlier). 0039 makes fills directional by order type
- **Import/export** — CSV, XLSX, JSON, both directions. Hostile-input tested

### Custom fields
`/fields` defines fields per entity type — text, number, date, currency,
percentage, dropdown, multi-select, checkbox, rating, notes, tag, colour.
Fields can be scoped to a strategy. Values live in `custom_fields` jsonb.
**The user's schema is data**, which is why every AI prompt renders fields
under the user's own labels.

### Analysis — free
- **`/dashboard`** — today's P&L, this month, open positions, cash, drawdown.
  Widget order and size are user-configurable
- **`/analytics`** — equity curve, max drawdown, R-multiple histogram, win
  rate, profit factor, expectancy, streaks, breakdowns by direction and
  strategy, monthly P&L
- **`/insights`** — *non-AI* statistical pass. Flags segments whose win rate
  deviates ≥15 points from the overall rate with ≥5 trades. Every insight
  traces back to a re-computable segment. Also carries the **mistake tracker**:
  labels from three sources (detected, a failed plan rule, hand-tagged), each
  with both sample sizes, and the expectancy comparison withheld below the
  floor rather than shown with a warning
- **`/goals`** — process and outcome goals evaluated against real trades.
  `at_most` goals fill *as the trader succeeds*
- **Plan rules** on `/strategies` — checkable rules attached to a strategy,
  evaluated per trade on `/trades/[id]`. Outcomes are pass / fail /
  **unevaluable**, and unevaluable is excluded from the denominator
- **Suggested tags** on `/trades/[id]` — deterministic, never AI. A moved stop
  or target, an exit short of the target on a winner, a position risked above
  the trader's own median. Offered with the reason; **written only when
  accepted**, dismissible, and dismissals are remembered
- **Trade timeline** on `/trades/[id]` — the edit snapshots diffed into a
  readable sequence. A field *absent* from an old snapshot is unknown, not
  null, so a column added later never manufactures a change that never happened
- **`/emotions`** — emotion logged before entry versus outcome
- **`/commissions`**, **`/account`** (cash ledger, data export, deletion)

### Analysis — paid
- **`/analytics`** — MAE/MFE excursions, trading-vs-account-growth (deposits
  separated from profit), drawdown *episodes* (how deep, how long, how many
  trades back), risk consistency, market regime
- **`/insights`** — Find My Edge: every dimension of the journal ranked, each
  with the sample size it rests on
- **`/strategies`** — scorecards per strategy
- **`/reports`** — printable weekly / monthly period report, assembled from the
  modules above rather than recomputed
- **AI**: `/ask`, the AI Review panel on `/trades/[id]`, and `/reviews`

**A note on the free/paid split**: the free tier keeps a working version of
everything it had. Paid layers sit *beside* free ones — `/insights` keeps its
deviation table, `/strategies` keeps its win-rate table, `/analytics` keeps its
equity curve and max drawdown. Nothing was taken away to create the paid plan.

### Supporting
- **Landing page** with hero, feature grid, how-it-works, pricing
- **Guided tour** for new users, plus a welcome modal
- **Keyboard shortcuts** — Gmail-style `g`-then-letter navigation chords
- **Admin** (`/admin/*`, gated on `is_admin`) — usage analytics, retention
  cohorts, feature usage, and hand-setting a user's plan
- **Self-hosted analytics** — page views, feature events, session heartbeats.
  No third-party tracker
- Dark/light theme; legal pages `/privacy`, `/terms`, `/cookies`, `/contact`

> **Removed 7 Sep 2026:** the Focused/Everything view-density toggle and its
> `CollapsibleSection` wrapper. Deep panels now always render expanded, which
> was already the CSS's own fallback. Do not reintroduce a `data-ui-mode`
> attribute or a `tl-ui-mode` storage key.

## Free vs paid

`user_settings.plan` is `'free' | 'paid'`. **There is no billing system** — no
Stripe, no webhooks, nothing that flips it automatically. It is set by hand with
the service-role key. The pricing card says plainly that the paid plan is not
purchasable yet, and it lists *only* features that are actually gated.

`isPaidUser()` (`src/lib/settings/plan.ts`) is the single gate. It is an
equality test against `"paid"`, not `!== "free"`, so an unrecognised value fails
**closed**.

**The gate list is not written from memory.** It is a grep of every
`isPaidUser` / `requirePaidUser` call site, and `PricingTeaser.tsx` carries the
same list with the same warning — a pricing card that promises something the
plan does not do is the one failure mode it cannot have.

| Surface | Gated |
|---|---|
| whole page | `/ask`, `/reviews`, `/reports` |
| `/analytics` | excursions, performance vs growth, drawdown episodes, risk, regime |
| `/insights` | Find My Edge (the deviation table and mistake tracker stay free) |
| `/strategies` | scorecards (the win-rate table stays free) |
| `/trades/[id]` | AI Trade Review, trade excursions |
| API | `ai-keys/*`, `ai-reviews/*`, `ask-ai`, `excursions` |

**Explicitly free, and must not be advertised as paid:** plan rules, the
mistake tracker, suggested tags, goals, the trade timeline.

## The AI subsystem

**The rule that shapes all of it: the app never owns an API key.** Every call
runs on the user's own key, on their own bill. There is no fallback key, no
proxy key, and no silent substitution of one provider for another.

### Keys and consent
- **Six providers**: OpenAI, Anthropic, Google AI Studio, Groq, OpenRouter,
  Cerebras. Four have standing free tiers (Groq, Cerebras, OpenRouter `:free`
  models, Google) and are surfaced as such — the feature is fully usable
  without paying anyone
- Keys are **AES-256-GCM encrypted at rest** under a server-only
  `AI_KEY_ENCRYPTION_SECRET`. Only the last 4 characters ever reach the client.
  Decryption happens server-side, immediately before the provider call
- **Ciphertext is bound to its owner** as GCM additional authenticated data, so
  a value moved between rows fails to decrypt. See the security section
- **Secret rotation is supported** via `AI_KEY_ENCRYPTION_SECRET_PREVIOUS`
- Keys are **test-called before being saved**, so a bad key fails at setup with
  a useful message rather than at question time with a confusing one
- A key the provider later rejects is **parked automatically**, because keys are
  verified once and never re-checked
- **Consent is recorded per provider** (`ai_provider_consents`), not per user
  and not per browser. Agreeing to send your journal to Groq is not agreement to
  send it to OpenAI. Enforced server-side on every request

### Shared plumbing
- `requirePaidUser()` — auth then plan, 401 before 403 so an anonymous caller is
  never told anything about plans
- `preflightProviderCall(supabase, keyId, userId)` — encryption configured, key
  resolvable and owner-bound, provider consented. Nothing leaves the server
  before this passes
- `providerErrorResponse()` — maps failures to distinct, actionable messages:
  bad key / retired model / out of room / provider down / unknown. **Provider
  error bodies are logged, never returned** — they can echo request content,
  which here means the user's journal
- Sliding-window rate limiting, per user, per warm instance

### 1. Ask Your Journal — `/ask`
Free-text questions answered from the user's real history, **as a
conversation** — follow-ups keep the thread, so "why?" and "break that down"
work.

- The journal is rendered into the *system prompt* and **rebuilt fresh every
  turn**, so a follow-up asked after logging a trade sees that trade. Only the
  words exchanged accumulate in history
- **History and journal share one character budget**, because both are re-sent
  on every turn and both bill the same per-minute allowance. History may take
  35%; oldest turns drop first, whole turns only; the journal never falls below
  8,000 chars
- **The budget is per provider**, sized against tokens-per-*minute* rather than
  the context window, which is almost never what fails:

| Provider | Budget | Why |
|---|---|---|
| Anthropic | 120k chars | Pay-as-you-go, large window, no meaningful TPM ceiling |
| OpenAI | 100k chars | Same |
| Google AI Studio | 100k chars | Free tier, but limits are RPM far more than TPM |
| OpenRouter | 30k chars | `:free` models vary by upstream |
| Groq | 20k chars | **8,000 tokens/minute free tier — the binding constraint** |
| Cerebras | 20k chars | Same shape |

- The journal is emitted newest-first in full detail until the budget is spent,
  then one line each, with the prompt stating honestly how many were
  abbreviated. Aggregates are computed over every row regardless
- **The prompt is a coach, not a search box.** It may draw on general trading
  knowledge (labelled as such), give direct "this is costing you money" advice,
  and take the length a question deserves. It may **not** fabricate a number,
  and it must quote figures from the data so they can be checked. Small samples
  must be flagged
- **Boundary:** coach the trader's process, don't forecast markets or pick
  positions. A light one-time disclaimer, not a hedge in every answer

### 2. AI Trade Review — panel on `/trades/[id]`
One closed trade, scored 0–100 on **execution, not outcome** — a winning trade
can be a bad trade. Six sub-scores (setup, entry, risk, exit, plan adherence,
discipline), what went well, what to improve, biggest mistake, best decision,
rule adherence, emotional analysis, and 1–3 actions for the next trade.

Three things make it specific rather than generic:
- **The trader's own baselines** — median size, median risk, average R, how
  often they close winners short of target — so "oversized" means oversized
  *for them*
- **Their own stated rules** — their strategies and descriptions. If they wrote
  none, rule adherence is reported as `unknown`, never guessed
- **Comparable past trades** — same ticker, same strategy
- Plus **the edit history**, which is the only place a moved stop is visible at
  all: the row holds the current stop, so without snapshots a stop walked down
  twice looks planned

**Blank fields are named explicitly** in the prompt. A model merely not told
about a stop reasons as though one existed; a model told "Stop loss: not
recorded" says so. Sub-scores are nullable for the same reason.

One review per trade; regenerating replaces it.

### 3. AI Period Review — `/reviews`
Weekly (last 7 local days), monthly (previous calendar month), or a custom
range. Produces a performance summary, biggest edge, biggest leak, behavioural
patterns, strategy breakdown, risk review, comparison against the preceding
equivalent period, and ≤3 priorities.

- **The app does the arithmetic, not the model.** Every aggregate, breakdown and
  period-over-period delta is computed in TypeScript and handed over finished.
  The prompt says "quote these numbers; do not recompute them"
- **Small samples are labelled, not hidden.** Every breakdown row carries its
  `n`; rows under 3 are marked `SAMPLE TOO SMALL TO CONCLUDE FROM` and the
  system prompt is bound to that marker. `insufficient_data` is a first-class
  confidence level, so a quiet week honestly reports no edge
- **Behaviour after a loss vs after a win** — average risk and hours-to-next-
  entry for each, with sample sizes. This is the evidence behind "revenge
  trading", stated as measured numbers rather than asserted
- Period history is kept (regenerating adds a version); trade reviews replace
- A pre-flight count runs server-side with **no provider call**, so the button
  reads "Review 9 trades" and an empty period is refused for free

### Structured output
Reviews are rendered into fixed sections, so the model's reply is validated
before anything is drawn.

**Native JSON mode is deliberately not used** — four different request shapes,
and support is weakest on exactly the free-tier models the feature leans on.
Instead: ask for JSON in the prompt, then read the reply well. A string-aware
brace scanner pulls the first balanced object through fences, preambles and
trailing chat; zod validates it.

Validation is **tolerant where it costs nothing, strict where it matters**,
because a repair costs a second call on the user's quota: a score of 105 is
clamped, `"Partially Followed"` is normalised, a numeric string is coerced — but
a reply with no assessment is rejected. One repair retry is allowed, gated on
both a wall clock and the size of what must be resent, and it sends **only** the
malformed reply and the schema, never the journal again.

### The provider interface
`askQuestion(apiKey, systemPrompt, question, options?)` across three
implementations — `anthropic.ts`, `google.ts`, `openai-compatible.ts` (which
backs OpenAI, Groq, OpenRouter and Cerebras).

`options` carries `{ maxTokens, timeoutMs, history }`. **`history` is where
multi-turn lives**, and each provider maps it differently: Anthropic passes
`user`/`assistant` straight through, **Google needs `assistant` → `model` and
text wrapped in `parts[]`**, OpenAI-compatible slots it between the system
message and the live question. `MAX_ANSWER_TOKENS` is 2,500 — sized with
headroom because several defaults are *reasoning* models that spend tokens
thinking out of the same budget.

### Prompt safety
Every system prompt states that journal text — including notes the trader wrote
themselves — is **data to be analysed, never an instruction to follow**. This
rule is not relaxed by any of the "make it more open" work. Model output is
rendered by `AnswerText`, which builds React elements from strings and never
touches `dangerouslySetInnerHTML`.

## Security posture

### Provider API keys — the most sensitive data here
These are spendable credentials belonging to someone else's account. Full
detail in `SECURITY.md` §6; the shape of it:

- **Database breach yields nothing usable.** AES-256-GCM ciphertext; the secret
  lives in the environment, never in the database. The stored `last_four` is 4
  characters of a 40+ character secret
- **Database *write* access also yields nothing usable.** Ciphertext is bound
  to its owner's user id as GCM additional authenticated data (format `v2`).
  Before that, an attacker with write access could copy a victim's
  `encrypted_key` into their own row and *spend* the key — no encryption secret
  required. Legacy `v1` values still decrypt and are upgraded in passing
- **A leaked secret is recoverable.** `AI_KEY_ENCRYPTION_SECRET_PREVIOUS` holds
  retired secrets (comma-separated) for decryption; keys are re-encrypted under
  the current secret as they are used. Rotation does not undo a leak already
  exploited — users must revoke and reissue in that case
- **Keys go to providers in a header, never a URL query parameter**, so they
  cannot land in request or proxy logs
- **Everything sent to Sentry is scrubbed** (`src/lib/observability/scrub.ts`,
  wired to `beforeSend` on server, edge and browser): every provider key
  format, our ciphertext envelope, JWT-shaped tokens, and any credential-named
  field. An event that cannot be scrubbed is dropped rather than sent
- **The limit, stated plainly:** an attacker with code execution on the server
  can read the environment and decrypt. This is unavoidable while the server
  calls providers on the user's behalf. Closing it means client-side encryption
  under a user passphrase, which costs a passphrase every session and rules out
  background AI work. That trade has not been made

### Everything else
- RLS on every table; the anon key is public by design
- Column-level grants guard `is_admin` and `plan` (see the data model)
- Service-role key is `server-only` and verified absent from the browser bundle
  by `npm run check:bundle`, which runs against the real build output
- Security headers in `next.config.ts`: HSTS, `nosniff`, `X-Frame-Options`,
  Referrer-Policy, Permissions-Policy, COOP
- **CSP is Report-Only** in `src/proxy.ts`, with a per-request nonce and
  `strict-dynamic`. Flipping it to enforcing is a one-header rename and is
  intended as its own deploy. `style-src` keeps `'unsafe-inline'` knowingly —
  React renders the `style` prop as an inline *attribute*, which a nonce cannot
  cover
- Ownership is proved by RLS, so a resource belonging to someone else returns
  **404, not 403** — a 403 would confirm the id exists and allow enumeration
- `/auth/confirm` resolves the `next` param and compares *origins* before
  redirecting — a prefix check on the raw string is bypassable with `/\evil.com`
- File handling (imports, exports, image uploads) is hostile-input tested
- Errors fail **closed**: an unrecognised plan denies, a failed consent lookup
  sends nothing, a missing encryption secret refuses before reaching crypto

### Uploads
MIME allowlist (JPEG/PNG/WebP/GIF — **SVG deliberately excluded**, it can carry
`<script>` and signed URLs open directly). 5 MB cap plus a 50-megapixel decode
ceiling against decompression bombs. Every upload is re-encoded through `sharp`,
which strips EXIF (phone photos of trading screens carry GPS) and proves the
bytes match the declared type. **Storage keys never use the client filename** —
`{userId}/{tradeId}/{uuid}.{ext}` with the extension derived from the validated
MIME type, so traversal and executable extensions are structurally impossible.
Private bucket, owner-scoped RLS, short-lived signed URLs.

### Rate limiting
Two layers, both on `src/lib/rate-limit.ts` (in-memory sliding window).

- **Blanket, in `src/proxy.ts`:** every `/api/*` request — 300/min per user id,
  60/min per client IP when unauthenticated. Scoped to `/api/` deliberately;
  the proxy matcher also covers page navigations and RSC payloads, and limiting
  those would break ordinary browsing
- **Per-route, tighter:** OCR 20/min, trade create 60/min, **trade PATCH
  240/min (autosave — deliberately loose)**, delete 60/min, image upload
  30/min, imports 10/min, xlsx parse 20/min, export 20/min, **account delete
  5/hour**, admin plan 60/min, plus the AI routes
- **Auth cannot be rate-limited here.** Sign-in, sign-up, reset and resend call
  Supabase Auth *directly from the browser* and never touch this app's server.
  The controls are Supabase dashboard rate limits and CAPTCHA — see
  `SECURITY.md` §1. Enabling CAPTCHA also requires passing `captchaToken` from
  the four auth screens, which they do not do yet
- **Known limitation:** counters are per warm instance, not global

## Accessibility

Brought up in the 7 Sep pass; keep it there.

- **Every error message is a live region.** `role="alert"` went from zero
  occurrences in the codebase to covering all 25 of them — 22 via
  `<FormError>` (`src/components/form-error.tsx`) and 3 bespoke. Background
  and autosave failures use `role="status"` (polite) instead, so they don't
  interrupt someone mid-sentence; there are 7 of those
- **Auth errors are mapped, never raw.** `src/lib/auth/error-messages.ts` turns
  Supabase codes into plain English and *never* passes the SDK's message
  through — a test asserts this directly. It also distinguishes a dropped
  connection from a wrong password
- **Every form control has an accessible name.** 18 orphan `<label>` elements
  (label with no `htmlFor`, wrapping nothing) were wired with `useId`.
  `FieldInput` takes an `id` for this reason
- **Modals are dialogs.** `src/lib/a11y/use-dialog.ts` provides focus trap,
  Escape, scroll lock and focus restore; used by the quick-trade, screenshot,
  welcome and lightbox dialogs. `PaidPlanModal` keeps its own equivalent
  implementation
- **Skip link + `<main>` landmark** in the root layout. App pages had neither.
  Page components must **not** add their own `<main>` — the layout owns the
  single landmark
- Focus rings are global (`:focus-visible` in `globals.css`)
- Contrast: light-mode `text-zinc-400` on near-white is ~2.6:1 and fails AA.
  Fixed where it was real text in a main flow. `dark:text-zinc-400` is fine and
  is the common case

## Known constraints and gotchas

1. **Migrations are applied by hand.** A file in git is not a live migration —
   check before assuming a newly added table or column exists
2. **No billing.** `plan` is set manually with the service-role key
3. **CSP is Report-Only**, not enforcing
4. **Rate limiting is per warm serverless instance**, not global
5. **26-second request ceiling.** AI routes budget ~22s for provider work
6. **Provider model IDs go stale silently.** A retired model surfaces as a
   failed request, not a failed build. `PROVIDER_MODELS` needs periodic
   re-verification against each provider's live `/models` list
7. **Investment-mode positions are excluded from every performance statistic**
8. **Yahoo market data is an undocumented public endpoint** with a best-effort
   symbol guess, correctable per ticker and remembered in localStorage
9. **No component or E2E tests** — unit tests over pure logic only
10. **Yahoo's `range=max` returns QUARTERLY bars, not daily.** Measured on
    AAPL: 168 bars at a 92-day median gap, against 2,513 daily bars at
    `range=10y`. Excursion maths on quarterly data would be silently,
    plausibly wrong, so `isDailyResolution()` guards it and the status enum
    has a `coarse_data` state to say so
11. **PostgREST upsert cannot infer a PARTIAL unique index.** 0001's plain
    unique constraint on `field_definitions` was dropped by 0017 and replaced
    with two partial indexes, so any `on conflict` against it must repeat the
    `where` predicate. This has cost a failed migration (`42P10`) once
12. **A `head: true` probe cannot prove a table exists** — always use a real
    `select`
13. **Writing to `trades` spends edit history.** See the trigger note
14. **`crypto.ts` imports `server-only`**, so any script importing it needs
    `tsx --conditions=react-server` (this broke `verify:ai-secret` once)
15. **Ask conversation history costs the same budget as the journal.** Raising
    one shrinks the other; on Groq's 8k TPM tier there is very little slack

## How to work on this codebase

1. Read the relevant `node_modules/next/dist/docs/` guide before framework code
2. Find the existing pattern and follow it — auth, validation, RLS, errors and
   comment style are consistent on purpose
3. Prefer reusing what exists (`fetchAllRows`, `getAnalyticsSummary`,
   `requirePaidUser`, `local-day.ts`, `enforceRateLimit`, `FormError`,
   `useDialog`, `failureMessage`) over writing a parallel version. A second
   implementation of a subtle calculation will drift, and two pages disagreeing
   about the same trades is worse than either being slightly wrong
4. Any new table or column needs a numbered migration with the manual-apply
   header, RLS enabled, and code that degrades until it is applied
5. Write comments that explain the decision, not the syntax
6. Add vitest coverage for pure logic, especially anything touching money,
   dates, or a security boundary
7. Every new error surface needs a human-readable message and `role="alert"`;
   every new form control needs a label; every new modal uses `useDialog`
8. Never let a feature fabricate a number. If the data isn't there, say so.
   A fabricated number is worse than no number — which in practice means:
   `null` rather than `0` for something unmeasurable, the sample size shown
   next to every comparison, a dimension refused outright when the data behind
   it does not exist, and explicit "why this is empty" copy instead of a blank
   panel
9. Prefer deterministic logic to AI wherever a result can be calculated from
   stored data. AI may *suggest*, but it must never silently write to the
   journal and never compute an authoritative financial metric
